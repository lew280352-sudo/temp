# StockLens บนคลาวด์ฟรี โดยไม่เปิดคอมค้างไว้

ใช้ Render **Free** รัน Docker และฐานข้อมูล **libSQL บน Turso Free** เก็บข้อมูลจริง การตั้งค่าและโค้ดพร้อมนำไป deploy ไม่ได้หมายความว่ามีบริการออนไลน์แล้ว ต้องตรวจ URL และข้อมูลหลัง deploy จริงอีกครั้ง

## ข้อจำกัดที่ตกลงใช้

- Render พักแอปหลังไม่มีคนใช้ 15 นาที การเปิดครั้งต่อไปอาจรอประมาณ 1 นาที ระหว่างพักรอบดึงข่าวและ Push หยุดทำงาน
- มีโควตาฟรีทั้งสองบริการ ใช้แผน Free และปิด paid overages ไม่เพิ่มแผนหรือซื้อโดเมนเพื่อให้ผ่านขั้นตอนนี้
- Render ฟรีเก็บไฟล์แบบชั่วคราว จึงห้ามใช้ไฟล์ SQLite บน Render เป็นฐานข้อมูลบัญชีจริง แอปจะปฏิเสธการเริ่มบน Render หากไม่มี Turso URL/token
- พอร์ต SMTP ทั่วไปถูกบล็อกบน Render ฟรี จึงปิด email-login OTP ใน profile นี้ บัญชีใช้รหัสผ่าน รหัสกู้คืน และ TOTP ที่ตั้งไว้เดิมได้เมื่อมีคีย์ MFA เดิม อีเมลผ่าน HTTP provider เป็นงานเพิ่มเติมที่ยังไม่ได้ตั้งค่า
- AI/ราคา/ข่าวเสริมต้องใช้ key ในโควตาฟรีของเจ้าของบัญชีเอง ไม่มี Ollama ในคอมตามขึ้นโฮสต์ และไม่มีการเปิด API billing ให้อัตโนมัติ

## 1. สร้างฐานข้อมูล Turso ฟรี

สร้างฐานข้อมูลชนิด **libSQL** ที่เข้ากับ `@libsql/client` (หาก dashboard มีตัวเลือก Turso engine ใหม่ ให้เลือก libSQL สำหรับ driver นี้) ตรวจว่าแผนเป็น Free และไม่ได้เปิด overages จากนั้นสร้าง database token

เก็บ `TURSO_DATABASE_URL` และ `TURSO_AUTH_TOKEN` ใน environment/secret ของเครื่องที่ทำ migration และ Render เท่านั้น ห้ามส่งในแชต Git หรือไฟล์ใต้ dist URL/token จาก SDK ของ engine อื่นใช้แทนกันไม่ได้ หากบัญชีไม่มีตัวเลือก libSQL ให้หยุดก่อน import และปรับ driver ภายใต้ database.mjs โดยทดสอบใหม่

## 2. เริ่มฐานใหม่ตามคำสั่งล่าสุด

วันที่ 6 พฤศจิกายน 2026 เจ้าของยืนยันว่าฐานข้อมูลเดิมไม่จำเป็น ให้เริ่มด้วยฐาน Turso libSQL ว่างใหม่ได้ จึงข้ามการค้นไฟล์ Windows และ import เดิม ไม่ลบหรือเขียนทับฐานเดิม

1. เพิ่ม Render และลงชื่อเข้าใช้บัญชีเจ้าของผ่านขั้นตอนอนุญาตของ Render
2. สมัคร [Turso](https://app.turso.tech) เลือกแผน Free และสร้างฐาน libSQL ชื่อ `stocklens` ให้ตรงกับ driver ของแอป
3. ตั้ง `TURSO_DATABASE_URL` และ `TURSO_AUTH_TOKEN` ใน secret/environment ของ Render และเครื่องพัฒนาที่ต้องใช้ ห้ามวาง token ในแชตหรือ Git
4. สำหรับฐานใหม่สร้าง MFA/VAPID keys ชุดใหม่ด้วยสคริปต์ configure ของแอป เก็บเฉพาะใน environment/secret แล้วใช้ค่าคงเดิมหลัง redeploy
5. Deploy source branch ที่ผ่าน CI ตั้งค่า origin ให้ตรง HTTPS จริง สมัครบัญชีใหม่ เลือกบริษัท แล้ว restart/redeploy เพื่อยืนยันว่าบัญชีและรายการยังอยู่

สถานะปัจจุบัน: ส่งตัวเลือก Render ให้เจ้าของเพิ่มแล้ว ยังไม่ได้ยืนยันการเชื่อม และยังไม่มี Turso credentials จึงยังไม่ถือว่าออนไลน์

## ขั้นตอนสำรองสำหรับกรณีเลือกย้ายข้อมูลเดิมภายหลัง

ส่วนนี้เป็นทางเลือก เจ้าของไม่ต้องทำเพื่อเริ่มฐานใหม่ตามคำสั่งปัจจุบัน หากเลือกย้ายภายหลัง ต้องใช้ปลายทางว่างที่แยกจากฐานใหม่ซึ่งเริ่มรับผู้ใช้แล้ว และต้องมีสำเนาจากเครื่องเดิม

1. ระบุตำแหน่งฐานข้อมูลต้นทางและแจ้งช่วงหยุดใช้งานก่อน cutover **หยุดแอปเดิมและทุก process ที่เขียนฐานข้อมูลก่อนสำรองรอบสุดท้าย** (Node: หยุด process; Docker: `docker compose stop stocklens`) กันผู้ใช้กลับเข้าต้นทางไว้ตลอดการย้าย ทั้งการสมัคร บันทึกรายการ กู้รหัสผ่าน และลบบัญชีต้องหยุดรับ จึงไม่มีการตอบว่าสำเร็จหลัง snapshot ที่จะนำไปใช้จริง
2. บนเครื่องเดิมใช้ซอร์สที่มีสคริปต์ backup และรัน `npm ci` ตาม lockfile จากนั้นใช้ `npm run backup` โดยชี้ DATABASE_PATH ไปที่ฐานข้อมูลเดิม **ขณะต้นทางหยุดรับการเขียนอยู่** ตรวจว่าสำรองสำเร็จและอ่านได้ หากเคยทดลอง import ด้วยสำเนาที่ทำตอนแอปยังเปิดอยู่ ให้ใช้สำเนารอบสุดท้ายนี้กับปลายทางว่างใหม่แทน
3. เก็บ `.env` เดิมไว้อย่างปลอดภัย โดยเฉพาะ `MFA_ENCRYPTION_KEY` และ VAPID คู่เดิม หากมีบัญชีเปิด TOTP แล้ว การใช้คีย์ใหม่จะถอดรหัส seed เดิมไม่ได้
4. ตั้ง Turso URL/token ใน `.env` บนเครื่องทำ migration ที่เป็นไฟล์ Git ไม่ติดตาม พร้อมคีย์ MFA/VAPID เดิม หยุดแอปปลายทางระหว่าง migration ใช้ฐานข้อมูล Turso ใหม่ที่ไม่มีบัญชี
5. รันจากโฟลเดอร์แอป:

```sh
node --env-file=.env scripts/import-database.mjs --source /absolute/path/to/verified-backup.sqlite
```

Windows ใช้ path ของไฟล์ backup จริง คำสั่งแสดงจำนวนแถวที่ย้ายเท่านั้น ไม่แสดงข้อมูลบัญชีหรือคีย์ ระบบปฏิเสธปลายทางที่มีข้อมูลผู้ใช้อยู่แล้ว หากขั้นตอนล้มเหลวจะไม่ commit ข้อมูลบางส่วน

6. ตรวจจำนวน users/user_state และทดลอง Login ด้วยบัญชีเดิมบนสภาพแวดล้อมทดสอบที่เชื่อมฐานข้อมูลปลายทาง ตรวจรายการติดตาม TOTP และรหัสกู้คืนตามขั้นตอนที่เหมาะสม เซสชันและ challenge เก่าจะไม่ถูกย้าย จึงต้อง Login ใหม่
7. คงต้นฉบับและสำเนาไว้จนยืนยันบริการใหม่สำเร็จ ไม่ลบหรือแทนที่ฐานข้อมูลบนเครื่องเดิมอัตโนมัติ

หากใช้ Docker ให้สำรองจาก volume เดิมหลังหยุด service โดยใช้ one-off container ที่รันเฉพาะสคริปต์ backup และ bind โฟลเดอร์ backups ออกมาที่เครื่อง (ไม่เริ่ม Node web server):

```sh
mkdir -p backups
docker compose stop stocklens
docker compose run --rm --no-deps -v "${PWD}/backups:/app/backups" stocklens node scripts/backup.mjs
```

ตัวอย่าง shell ด้านบนใช้กับ Bash; บน PowerShell สร้างโฟลเดอร์ backups ก่อน แล้วใช้ path เต็มของโฟลเดอร์ใน `-v` ตรวจว่าไฟล์สำรองอยู่บนเครื่องก่อนลบ one-off container อย่าใช้ `docker compose down -v` กับต้นทาง เพราะจะลบ volume ข้อมูลเดิม

หาก import แจ้งว่าคีย์ MFA/VAPID เดิมไม่พร้อม ให้จัดเตรียมคีย์เดิมผ่านช่องทางลับ ไม่ลบข้อมูล MFA/อุปกรณ์ Push เพื่อบังคับให้ import ผ่าน

### การย้อนกลับโดยรักษาข้อมูล

- ก่อนเปิดรับผู้ใช้บนปลายทาง: หากตรวจ migration ไม่ผ่าน ให้หยุดปลายทางก่อน แล้วจึงเปิดแอปเดิมจากฐานข้อมูลต้นฉบับที่หยุดเขียนไว้ ต้นทางยังไม่มีการเปลี่ยนแปลงหลังสำเนารอบสุดท้าย
- หลังปลายทางเริ่มรับการเขียนแล้ว: คงต้นทางเดิมปิดไว้ หากต้องย้อนกลับให้หยุดรับการเขียนที่ปลายทางด้วยและ export ข้อมูลล่าสุดก่อน วางแผน restore/reconcile ไปยังฐานทดสอบว่างและตรวจข้อมูลที่รับเพิ่มทั้งหมด **ห้ามเปิดฐานต้นทางเก่าทับทันที** เพราะจะทำให้ข้อมูลที่ปลายทางตอบรับสำเร็จแล้วหายไป
- เปิดให้ใช้งานได้เพียงฝั่งเดียวในแต่ละช่วง และบันทึกเวลา freeze / final backup / เปิดปลายทางไว้ในบันทึก cutover ที่เจ้าของเก็บเองโดยไม่รวมคีย์

## 3. สร้างบริการ Render Free

เชื่อมรีโป GitHub และใช้ render.yaml ของ commit ที่ผ่าน CI แล้ว ตรวจ `plan: free` และไม่มี disk หรือบริการเสริมแบบเสียเงิน URL `onrender.com` ที่ Render จัดให้ใช้ HTTPS ได้โดยไม่ซื้อโดเมน

ใส่ Turso URL/token ใน secret ของบริการ พร้อม MFA/VAPID keys เดิมหากใช้ ตั้งคีย์ API เสริมเฉพาะที่มีโควตาฟรี ตั้ง `EMAIL_LOGIN_OTP_ENABLED=false` ตาม blueprint

Render กำหนด PORT และ RENDER_EXTERNAL_URL ให้ แอปใช้ URL นั้นเป็น APP_ORIGIN หากไม่ได้กำหนด APP_ORIGIN เอง เมื่อเปลี่ยนเป็นโดเมนอื่นจึงค่อยตั้ง APP_ORIGIN ให้ตรงกับ HTTPS URL ใหม่

ค่า TRUST_PROXY_HOPS เริ่มที่ 0 เพื่อไม่เชื่อ header ที่ผู้ใช้ส่งเอง ต้องตรวจ topology ของ Render ที่ใช้งานจริงก่อนตั้งจำนวน hops และทดสอบ throttling แยกผู้ใช้หลัง proxy เดียวกัน ห้ามตั้งเพียงเพื่อให้การจำกัดคำขอหายไป

## 4. ตรวจรับก่อนใช้งาน

- สถานะ deploy สำเร็จ HTTPS เปิดได้ และ `/api/health` ตอบว่า ok โดยเชื่อมฐานข้อมูลจริง
- Login ด้วยบัญชีเดิมและตรวจรายการติดตาม ข้อมูลบัญชีหนึ่งเปิดจากอีกบัญชีไม่ได้
- บันทึกการเปลี่ยนแปลง ออกจากระบบ เข้าใหม่ แล้ว restart/redeploy บริการและตรวจว่าข้อมูลยังอยู่
- ทดลองกับมือถือจริง ดูข้อมูลเก่า/บริการที่ยังไม่ใส่ key และข้อความเกี่ยวกับ Push ที่อาจพัก
- ตรวจว่า logs ไม่มี token/password และไม่ใช้บัญชีจริงทดสอบการลบข้อมูล

## Backup / Restore ของฐานข้อมูลออนไลน์

`npm run backup` ทำ SQLite online backup สำหรับ local เท่านั้น เมื่อ TURSO_DATABASE_URL ถูกตั้งจะหยุดพร้อมคำแนะนำ แทนการสร้างสำเนาไฟล์ local ที่ไม่เกี่ยวกับข้อมูล cloud

ใช้คำสั่ง export ของ Turso ตาม engine และ CLI เวอร์ชันที่ติดตั้ง เช่นการ dump ฐานข้อมูล libSQL ด้วย `turso db shell <database-name> .dump` ไปยังไฟล์ที่เจ้าของบัญชีควบคุม โดยดู [คู่มือ import/export](https://docs.turso.tech/cli/db/shell) และ [การสำรอง/กู้คืน](https://docs.turso.tech/features/point-in-time-recovery) ของผู้ให้บริการ เก็บคีย์ MFA/VAPID แยกจากสำเนาฐานข้อมูลอย่างปลอดภัย ไม่ฝากสำเนาสำคัญไว้บน Render filesystem

ทดลอง restore ลงฐานข้อมูลทดสอบแยกก่อนใช้จริง หากสำเนามี sessions เก่าให้เพิกถอน sessions และ pending login challenges ก่อน cutover วิธี import ของแอปจะไม่ย้ายสองตารางนี้ ไม่ restore ทับฐานข้อมูลที่มีบัญชีใช้งานอยู่

## เมื่อเต็มโควตาหรือเชื่อมฐานข้อมูลไม่ได้

แอปต้องแสดงข้อผิดพลาดและไม่บอกว่าบันทึกสำเร็จ ไม่สร้างบัญชีว่างใน local แทน หยุดคำขอที่ไม่จำเป็นและรอโควตากลับมาตามเงื่อนไขผู้ให้บริการ ไม่เปิด billing หรือใช้ระบบ keep-alive เพื่อเลี่ยงข้อจำกัดของแผนฟรี
