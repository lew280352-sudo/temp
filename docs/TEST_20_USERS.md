# ผลทดสอบผู้ใช้จำลอง 20 คน

รายงานนี้เป็นผลก่อนย้ายไปหุ้นสหรัฐฯ ผลรุ่น US PWA 0.3 ล่าสุดอยู่ที่ [RELEASE_03.md](RELEASE_03.md) และ [users20-pwa.json](test-results/users20-pwa.json)

วันที่ทดสอบ: 18 ตุลาคม 2026 (เวลาไทย) เป็นการทดสอบอัตโนมัติด้วย Playwright ไม่ใช่การสัมภาษณ์ผู้ใช้จริง และไม่ใช่การรับรองความพร้อม production

## ปัญหาที่พบและแก้จริง

ตัวจำกัดเดิมนับ Register และ Login ของทุกบัญชีรวมกันไม่เกิน 20 ครั้งต่อ IP ใน 15 นาที เมื่อทุกบัญชีสมัครสำเร็จพร้อมกันครบ 20 คำขอ เพดานหมดก่อนเริ่ม Login ผู้ใช้ทั้งกลุ่มได้รับ HTTP 429 แม้แต่ละบัญชีจะเพิ่งใช้แอปครั้งแรก ปัญหานี้เกิดได้เมื่อผู้ใช้แชร์ Wi-Fi หรืออยู่หลัง reverse proxy เดียวกัน

ปรับเป็นสองเพดานร่วมกัน:

- สูงสุด 10 ครั้งต่อบัญชี+IP ใน 15 นาที
- สูงสุด 200 ครั้งรวมต่อ IP ใน 15 นาที

ยังรวมคำขอ Register/Login ทั้งสำเร็จและล้มเหลว และยังไม่เชื่อ X-Forwarded-For ที่ส่งมาเอง ไม่ได้ปิด rate limiting เพื่อให้ผลทดสอบผ่าน ทดสอบเพิ่มว่าบัญชีเดียวเกินโควตายังถูกบล็อก บัญชีอื่นยังใช้ได้ และการกระจายคำขอหลายอีเมลยังติดเพดาน IP

## สถานการณ์ที่ตรวจ

ทุกบัญชีทำ flow พื้นฐาน:

1. เปิด Register และตรวจไม่มีการล้นแนวนอน
2. สมัครบัญชีและ Login ด้วย cookie/session แยกจากผู้ใช้อื่น
3. เพิ่ม PTT ด้วยจำนวนหุ้นเฉพาะบัญชี
4. ค้นหาภาษาไทย และตรวจกรณีไม่พบบริษัท
5. เพิ่ม URL เฉพาะบัญชี และตรวจ URL ซ้ำไม่ถูกบันทึกเพิ่ม
6. ใส่ URL localhost ที่ไม่อนุญาต ตรวจว่า server ปฏิเสธและข้อมูลเดิมยังอยู่
7. บันทึกเวลาแจ้งเตือนที่ต่างกันแต่ละบัญชี
8. Reload แล้วตรวจหุ้น URL เวลาแจ้งเตือน และอีเมลตรงบัญชี
9. ลองส่ง userId ของบัญชีอื่นไปบันทึก ต้องถูกปฏิเสธ 409
10. Export ต้องเป็นข้อมูลตนเองและไม่มี password hash/session token
11. Logout ต้องล้างข้อมูลส่วนตัวบนหน้าจอและปฏิเสธ Export ด้วย 401
12. Login ใหม่แล้วข้อมูลที่บันทึกไว้ยังอยู่ ไม่มี JavaScript page error

## ตัวเลขหลังแก้

- HTTP 200: 284; HTTP 201: 20
- HTTP 400: 20 ครั้งจาก URL ที่จงใจกรอกผิด
- HTTP 401: 20 ครั้งจากการ Export หลัง Logout
- HTTP 409: 24 ครั้งจากการส่ง userId ผิดบัญชี 20 ครั้ง และ revision เก่า 4 ครั้ง
- ไม่มี HTTP 429 หรือ 5xx ใน flow ผู้ใช้ปกติรอบนี้
- เวลา API ที่สำเร็จเท่านั้น: median 91 ms, p95 1,656 ms, สูงสุด 2,525 ms

เวลาเป็น end-to-end request timing ที่ Chromium วัดบน localhost รวมงาน auth hashing และภาระจาก 20 contexts ไม่ใช่ CPU time ฝั่ง server ไม่รวมคำขอ 4xx ใน percentile และไม่มี latency threshold เป็นเกณฑ์ผ่าน ชุด tests ฝั่ง server ทั้ง 7 รายการผ่านแยกต่างหาก

## สภาพแวดล้อมและข้อจำกัด

- Windows, Node.js v24.18.0, Microsoft Edge แบบ headless บนเครื่องเดียว
- 10 contexts ขนาด 1440×1000 และ 10 contexts ขนาด 390×844; เป็น mobile viewport ไม่ใช่ Safari/iPhone หรือ Android จริง
- เซิร์ฟเวอร์ Node.js instance เดียว SQLite บนดิสก์แยกเฉพาะรอบ ใช้ IP localhost เดียวกัน
- ทั้ง 20 contexts เปิดค้างพร้อมกัน และทำงานแบบขนานในแต่ละช่วง ไม่มีการทดสอบเป็นผู้ใช้จริง 20 คนบนเครือข่ายต่างกัน
- บล็อกการดาวน์โหลด Google Fonts ในชุดนี้เพื่อแยกผลเครือข่ายภายนอก ใช้ fallback font; ไม่วัดเวลาการโหลด font จริง
- ไม่มีบัญชีหรือฐานข้อมูลจริงถูกแก้ไข ไม่มีการอ่าน URL ข่าวภายนอกหรือเรียกโมเดล AI
- ยังไม่ได้ทดสอบโหลดหลายชั่วโมง ผู้ใช้หลักร้อย/พัน ปริมาณข่าวจริง เครือข่ายช้า โฮสต์ production หรือความแม่นยำ AI
